# تأمين قاعدة البيانات — المرحلة 1

هذا المجلد يحوي سكربتات SQL تُشغَّل **يدوياً** من Supabase → SQL Editor (لم يُنفَّذ أي شيء على قاعدتك).

| الملف | الغرض |
|---|---|
| `00_preflight.sql` | فحص قبل التنفيذ (قراءة فقط) |
| `01_phase1_hardening.sql` | التأمين الفعلي (معاملة واحدة، يمكن إعادة تشغيله) |
| `02_verify.sql` | فحص بعد التنفيذ (قراءة فقط) |
| `99_rollback_phase1.sql` | تراجع طارئ (يفتح الصلاحيات من جديد — حل مؤقت فقط) |

## ماذا يغلق هذا السكربت؟

1. **القراءة والكتابة المجهولة**: أي شخص بالمفتاح العام كان يقرأ/يكتب في employees وcompanies وusers وemployee_links وattendance وprofessions. تُحوَّل كل السياسات المفتوحة للمجهول إلى «مسجّلو الدخول فقط» (سلوك المستخدمين لا يتغير). المستثنى عمداً: `app_settings` (مفتاح تفعيل التسجيل الذاتي) و`report_snapshots` (رابط تقرير QR).
2. **رفع الصلاحيات**: كان أي مستخدم مسجّل يستطيع تغيير دوره إلى مدير أو تعديل صلاحيات الأدوار. الآن تغيير الدور/الحالة وإدارة المستخدمين وتعديل `role_permissions` للمدير/المسؤول فقط، ومحمي أيضاً بـ trigger.
3. **ثغرة `handle_new_user`**: كان الدور يُؤخذ من بيانات التسجيل القادمة من المتصفح (أي شخص يسجّل نفسه كـ super_admin). الآن كل حساب جديد = موظف قيد المراجعة، والمدير يضبط الدور بعد الإنشاء (وهذا ما يفعله التطبيق أصلاً).
4. **حسابات قيد المراجعة/المرفوضة**: شاشتا دخول المسؤول والشركة لا تفحصان الحالة، فتمنعها الآن «بوابة موافقة» على الجداول نفسها.
5. **المستندات**: حاويتا `employee-documents` و`company-documents` تصبحان خاصتين (روابط موقّعة تنتهي بعد 5 دقائق)، والرفع المجهول مغلق.

## ترتيب التنفيذ (مهم)

1. **انشر ملفات التطبيق الجديدة أولاً** (GitHub → الاستضافة): `app/shared/storage-docs.js` (جديد) وكل ملفات الصفحات والسكربتات المعدّلة. بدونها تتعطل روابط المستندات بعد الخطوة 4.
2. خذ **نسخة احتياطية** (Supabase → Database → Backups).
3. شغّل `00_preflight.sql` وراجع:
   - الاستعلام 1: الأدوار. إن وُجد دور مخصّص (غير super_admin/admin/company/employee) **يدير المستخدمين أو الصلاحيات**، عدّل الدالة `can_manage_users()` في الملف 01 لتشمله، وإلا سيفقد هذه الصلاحية.
   - الاستعلام 2: حسابات Auth بلا صف في `users` سيُحجَبون بعد التنفيذ؛ أنشئ لهم صفوفاً أو اتركهم.
   - الاستعلام 3: المستخدمون قيد المراجعة حالياً.
4. شغّل `01_phase1_hardening.sql` كاملاً. أي خطأ يلغي كل شيء ولا يترك حالة نصف مطبّقة.
5. شغّل `02_verify.sql`: يجب أن يظهر في الاستعلام 1 صفّان فقط (`app_settings` و`report_snapshots`)، والحاويتان `public = false`.
6. اختبر يدوياً (متصفح جديد/نافذة خاصة):
   - دخول كل دور: مدير عام، مسؤول، شركة، موظف.
   - فتح مستند موظف وشركة من الشاشات (يجب أن يفتح بنافذة جديدة).
   - إضافة موظف وشركة ومستخدم جديد من النظام (كلمة المرور المؤقتة تظهر مرة واحدة — انسخها).
   - تسجيل موظف ذاتي من صفحة التسجيل ثم قبوله من «طلبات التسجيل».
   - فتح رابط تقرير QR بدون تسجيل دخول.
   - تعديل صلاحيات الأدوار من حساب مدير.
7. إن تعطّل شيء ولم يُحل: `99_rollback_phase1.sql`، ثم أخبرني بالخطأ.

## ملاحظات

- أي حساب يُنشأ من لوحة Supabase مباشرة سيصبح «موظف قيد المراجعة»؛ عدّل دوره وحالته من شاشة المستخدمين أو من Table Editor.
- الروابط القديمة المباشرة للمستندات (`/object/public/...`) لن تعمل خارج التطبيق؛ داخل التطبيق تتحوّل تلقائياً لروابط موقّعة.
- ما يزال المستخدم المسجَّل المعتمد يستطيع قراءة صفوف كل الشركات/الموظفين (عزل لكل دور بحسب الشركة هو **المرحلة 2**)، وتنظيف إدخال النصوص في الواجهة (XSS) هو **المرحلة 3**.
