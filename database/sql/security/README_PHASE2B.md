# المرحلة 2ب — فرض صلاحيات الأقسام داخل قاعدة البيانات

**المتطلب:** المرحلتان 1 و2 منفَّذتان. التشغيل يدوياً من Supabase → SQL Editor بعد نسخة احتياطية.

## ماذا تفعل؟
كان الموظف ذو الدور المحدود (مثلاً «محاسب» بلا حذف فواتير) يتقيّد بصلاحياته في الواجهة فقط؛ وأي أحد
بالمفتاح العام يتجاوزها بطلب مباشر. الآن تتحقق قاعدة البيانات من نفس الصلاحيات (عرض/إضافة/تعديل/حذف) المحفوظة
في `role_permissions`، بنفس منطق `Permissions.can` في `permissions.js`:

- **المدير العام (`super_admin`)**: كل شيء دائماً.
- **دور بلا صف في `role_permissions`**: مسموح بكل شيء (كما تفعل الواجهة).
- **الصيغ القديمة** (قسم مجرّد، `action:attendance_bulk_add`، `add:finance_invoices`، صلاحية القسم الأب) تُترجَم بنفس القواعد.
- **الشركة والموظف**: لا يتأثران (يحكمهما عزل المرحلة 2).
- **الكتابة** (إضافة/تعديل/حذف): كل جدول مربوط بكل صلاحية تستخدمه شاشاته فعلاً (اتحاد). مثال: تحديث `employees` مسموح لمن يملك
  `edit:employees` أو `delete:employees` (القائمة السوداء) أو `edit:employee_links` أو `edit:end_employee_link`...
- **القراءة**: تُقيَّد فقط جداول لا تقرؤها لوحة التحكم (المفتوحة لكل الأدوار): الفواتير، التحصيل، الرواتب، القائمة السوداء،
  تذاكر الدعم، قوالب المهام، طلبات التسجيل. أما الموظفون والشركات والمهام والحضور فتبقى قراءتها مفتوحة لموظفي النظام لأن لوحة
  التحكم نفسها تعرضها لكل دور.

## إضافات أمنية في نفس السكربت
- **`role_permissions`**: الكتابة للمدير العام فقط (كشاشة «الأدوار والصلاحيات» المقفلة عليه). حاجز مطلق لا تتجاوزه سياسات قديمة.
- **منع الترقية الذاتية**: المسؤول (`admin`) لا يستطيع إنشاء أو تعديل أو حذف حساب `super_admin`.
  ⚠️ إن كان مسؤولون (غير المدير العام) يُنشئون مديرين عامّين عمداً من شاشة المستخدمين، فهذا سيتوقف — أنشئهم بحساب المدير العام.
- **`users`**: كتابة صف شخص آخر تتطلب أحد الأقسام التي تنشئ/تعدّل الحسابات (`add:users`، `add:employees`، `add:companies`...)، وصفّك أنت دائماً مسموح.

## الترتيب
1. نسخة احتياطية.
2. شغّل `12_phase2b_permissions.sql` كاملاً (معاملة واحدة، يمكن إعادته).
3. اختبر بحساب **كل دور مخصّص عندك** (وبالأخص دور محدود): افتح شاشاته المسموحة وجرّب إضافة/تعديل/حذف؛ ثم جرّب ما ليس له (يجب أن يفشل
   بخطأ «violates row-level security» أو لا يتغيّر شيء). ثم بحساب المسؤول `admin`.
4. إن تعطّلت شاشة مسموحة لدور ما: شغّل `12_rollback_phase2b.sql` وأرسل لي اسم الشاشة والدور، وسأُضيف الصلاحية المفقودة للجدول.

## ملاحظات
- أول ما قد تلاحظه: دور مخصّص كان يستطيع «بالخطأ» فعل ما لا تسمح له صلاحياته (لأن الواجهة كانت تُخفي الزر فقط)؛ سيُمنع الآن — هذا المقصود.
- ما زالت إدارة الحسابات (إنشاء/تعديل مستخدمين) مقتصرة على `admin`/`super_admin` من المرحلة 1 (`can_manage_users`). أدوار مخصّصة لديها `add:users`
  لن تنشئ حسابات إلا إن عدّلت تلك الدالة (أخبرني إن أردتها).
